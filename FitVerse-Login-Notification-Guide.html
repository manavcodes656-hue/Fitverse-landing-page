Section 01

What Are We Building?

A security feature. Whenever someone signs in to a FitVerse account, that account's owner gets an email telling them it happened. If it was them, they ignore it. If it wasn't, they now know within seconds that somebody else has their password.

1.1  What happens when a user logs in

Right now, when a FitVerse user types their email and password:

  1. Supabase checks whether the password is correct.
  2. If it is, Supabase creates a session — a record saying "this person is now signed in".
  3. The app lets them in.
  4. Nothing else happens. Nobody is told.

After you build this feature, one more thing happens, quietly, in the background:

  1. Your system notices the new session, records it, and emails the user.

1.2  Why we need login notifications

Passwords leak. People reuse them across sites, sites get breached, and lists of email/password pairs get traded. When somebody uses a stolen FitVerse password, the login looks completely normal to your system — the password is correct, after all.

A login notification is the one thing that closes this gap. It goes to an address the attacker (usually) doesn't control, and it turns a silent break-in into something the real owner finds out about immediately.

Why this matters more for FitVerse than for most apps

FitVerse stores health data — what people eat, how they sleep, their body metrics, and (with the For Women module) menstrual cycle information. This is among the most sensitive categories of personal data there is. A break-in here is not "someone saw my workout log" — it is a genuine privacy harm. Login alerts are a standard, expected protection for products holding this kind of data.

1.3  What the user receives

One short email: "Your FitVerse account was signed in to just now", with the time, the device, and a big obvious button — "This wasn't me — reset my password". Nothing technical, nothing alarming if it was them. Full design in Section 08.

1.4  What FitVerse receives

You originally wanted an email to your team for every single login. I am going to recommend something different — one summary email per day instead of one per login. The full reasoning is in Section 09, but the short version is: an inbox that gets a thousand emails a day is an inbox nobody reads.

1.5  Why the backend must handle this

The obvious approach is to put the code in the app: "after login succeeds, send the email." This is the wrong approach, and it is worth understanding why before you build anything.

Concept: client-side vs. server-side detection
What "client-side" means
Code that runs on the user's own phone or browser — inside the FitVerse app itself.
What "server-side" means
Code that runs on machines you control — Supabase's servers and your Next.js backend. The user cannot see or change it.
Why client-side fails here
Two reasons. First, it fires at the wrong times. Supabase's client library has a listener called onAuthStateChange that emits a SIGNED_IN event. It sounds perfect, but it also fires when the app simply opens with a saved session, and sometimes when a browser tab regains focus. You would email people every time they opened the app. Second, it can be skipped. A modified app just doesn't make the call, and the alert silently never sends.
The principle
A security alert that can be skipped is not a security feature. It must be triggered by something the attacker cannot switch off.

1.6  The whole system, in one picture

User types email + password in the FitVerse app
        |
[1] Supabase Auth checks the password -> creates a NEW SESSION
        |
[2] A database trigger notices "a new session row appeared"
        |     (sends an HTTP POST, with a secret header)
        v
[3] Your Next.js API route receives it
        |
[4] Saves a row in login_events   <-- unique session_id blocks duplicates
        |
[5] Resend emails the user "new sign-in detected"
        |
[6] Row is updated: email sent / failed
        |
[7] Separately, once a day, a digest email goes to your team

Notice that steps 2–7 happen after the user is already logged in. That ordering is deliberate, and it is what guarantees the rule we will come back to repeatedly: a broken email system can never stop somebody signing in.

Section 02

The Recommended Approach

You need Supabase, a trigger, a backend route, a database table, and Resend. These are not competing options — each does a different job. The only real decision is how Supabase tells your backend that a login happened, and Section 04 settles that.

2.1  The role of each component

ComponentIts one jobWhat you do with it
Supabase Auth Checks the password and creates the session. Nothing. You do not modify how login works at all. This is important — you are adding a listener, not changing authentication.
Database trigger + pg_net The doorbell. Notices a new session and calls your API. Write a small database function and attach it to the sessions table. Runs on Supabase's servers, so the app cannot skip it.
Next.js API route The brain. Verifies the call is genuine, records it, sends the email. Create one new file, modelled on your existing waitlist route.
Supabase database Stores everything, and enforces the no-duplicates rule. Run one SQL migration.
login_events table The logbook. Also your duplicate-blocker and your retry list. Created by that migration. Protected by Row Level Security.
Resend The postman. Actually delivers the email. Already wired up in your project. You verify the domain and add a sender address.
Admin digest One summary email per day to your team. Build this last, after user emails work.

2.2  Why this architecture suits FitVerse specifically

This is not a generic recommendation. It is shaped by what your project already contains:

  • You already have Resend working. Your waitlist form sends a welcome email through it today. No new email provider, no new account, no new cost.
  • You already have a server-side Supabase admin client. lib/supabase.ts exposes getSupabaseAdmin(), which can write to any table. Exactly what the new route needs.
  • You already have this exact route pattern. app/api/waitlist/route.ts validates input, writes to Supabase, catches duplicate-key errors, hashes IP addresses and sends an email without letting failure break the main action. Your new route is that file with a different trigger.
  • You are a small team. Keeping everything in Next.js means one language, one deployment, one place to look when something breaks.
Tip — the honest summary

You have already built this once. The login notifier is your waitlist route with a different trigger and a different email template. When you get stuck, open the waitlist route and look at how it solved the same problem.

2.3  Why not a Supabase Edge Function?

Supabase offers Edge Functions — small programs that run on Supabase's own infrastructure. This would also work, and it is a perfectly respectable choice. I am not recommending it here because Edge Functions are written in Deno, deployed separately from your Next.js app, with their own secrets to manage and their own logs to check.

That means two stacks to maintain instead of one, for no functional gain. For a small pre-launch team, one stack beats two. If your team later grows and wants the notification logic to live closer to the database, moving it to an Edge Function is a straightforward migration.

Warning — do not use onAuthStateChange

If you search online for "Supabase send email on login", most answers will tell you to listen to onAuthStateChange in your app. Do not do this. As explained in Section 1.5, it fires on app open and session restore, and it can be bypassed. Every problem it creates is one the server-side approach simply does not have.

Concept: what NEXT_PUBLIC_ means, and why it matters
What it is
A prefix Next.js looks for on environment variable names.
What it does
Any variable starting with NEXT_PUBLIC_ gets baked into the JavaScript sent to the browser. Anyone can open developer tools and read it. Variables without the prefix stay on the server and are never sent anywhere.
Why you must care
SUPABASE_SERVICE_ROLE_KEY can read and write every row in your database, ignoring all security rules. If it ever got the NEXT_PUBLIC_ prefix, you would be publishing full database access to every visitor.
The good news
Your project already gets this right. lib/supabase.ts reads SUPABASE_SERVICE_ROLE_KEY with no prefix, and lib/resend.ts reads RESEND_API_KEY with no prefix. Keep it that way.
Warning — fix this before adding any new secret

Your .gitignore ignores .env*.local but not a plain .env file. If anyone on the team ever creates .env, your service role key and Resend key get committed to git — and once a secret is in git history, it is compromised forever, even if you delete it later.

Add .env to .gitignore as step one.

Section 04 · Step 1

Supabase Login Detection

This is the one genuine decision in the whole project: how does Supabase tell your backend that a real login just happened? There are two candidates. I recommend one of them clearly, and explain the trade-off honestly.

4.1  Check whether the Password Verification Auth Hook exists

Concept: an Auth Hook
What it is
A place where Supabase lets you plug your own code into the login process itself.
Why it might help
The "Password Verification Attempt" hook fires every time Supabase checks a password, telling you which user and whether the password was correct. That is very close to what we want.
The catch
Availability varies by Supabase plan and version, so you must check rather than assume.

WHAT YOU NEED TO DO

  1. Open your Supabase Dashboard and select your project.
  2. In the left sidebar, click Authentication.
  3. Look for a sub-item called Hooks (it may be labelled "Auth Hooks", and depending on your dashboard version it may live inside Authentication settings rather than as its own menu item).
  4. If hooks are available, you will see a list of hook types — typically Send Email, Send SMS, Custom Access Token, MFA Verification Attempt, and Password Verification Attempt.
  5. Write down what you find. You need this answer recorded even though, as explained next, you are probably not going to use it.

How to tell it is unavailable: the Hooks section is missing entirely, or the hooks are shown greyed out with an "upgrade your plan" prompt.

Important — the dashboard changes

Supabase redesigns its dashboard regularly, so exact menu labels may differ from what is written above. Look for the concept, not the exact wording: a section under Authentication that lists pluggable hooks. I am deliberately not inventing precise button names I cannot verify.

4.2  The decision — and my recommendation

✓ Recommended option

Use a database trigger on new sessions — even if the Password Verification Hook turns out to be available in your project.

Here is the honest comparison:

CapabilityPassword HookNew-session Trigger
Tells you a password specifically was checkedYesNo (covers all login types)
Gives you a session IDNoYes
Gives you device / browser infoNoYes
Gives you the IP addressNoYes
Available on every Supabase planMust verifyYes
Why the trigger wins

The password hook fires before a session exists. That means no session ID — and your entire duplicate-prevention design depends on that session ID being available. It also means no device information to put in the email. The trigger simply gives you more of what you need.

And alerting on every login is better security, not worse. If you add Google sign-in later, someone breaking into a Google account is exactly who you want to catch. Restricting alerts to password logins would be a downgrade.

Fallback option — for later, not now

If you later want to distinguish "signed in with a password" from "signed in with Google", the Password Verification Hook is where you would get that signal. Note whether it exists in your project, then set it aside. Do not build on it today.

4.3  Verify what your auth.sessions table contains

Do this before writing anything else. Supabase's internal tables vary between versions, so confirm rather than assume.

WHAT YOU NEED TO DO

Dashboard → SQL Editor → New query → run this read-only query:

select column_name, data_type
from information_schema.columns
where table_schema = 'auth' and table_name = 'sessions'
order by ordinal_position;

You are looking for these columns:

  • id — the session ID. Essential.
  • user_id — who logged in. Essential.
  • created_at — when. Essential.
  • user_agent — the device/browser. Nice to have.
  • ip — the IP address. Nice to have.
Tip

If user_agent and ip are missing, everything still works — you simply won't have device information in the email. Record what you find; the next step depends on it.

4.4  Enable the pg_net extension

Concept: pg_net
What it is
An add-on for PostgreSQL that lets the database itself make HTTP requests to the internet.
Why we need it
Your database needs to phone your API route when a login happens. Databases normally cannot do this.
How it helps safety
net.http_post queues the request and returns immediately. It does not sit and wait for a reply, so it can never slow down or block a login.

WHAT YOU NEED TO DO

Dashboard → Database → Extensions → search for pg_net → enable it.

4.5  Store your secret inside Supabase Vault

Concept: the shared secret
What it is
A long random password that only Supabase and your API route know.
Why we need it
Your API endpoint sits on the public internet. Without a secret, anyone could call it and trigger fake "someone logged into your account!" emails to your users — a perfect phishing tool.
How it works
Supabase sends the secret in an HTTP header. Your route compares it to its own copy. No match, no action.

WHAT YOU NEED TO DO

  1. Generate a random string of at least 32 characters using a password manager. Do not type one yourself — human-chosen strings are guessable.
  2. Go to Dashboard → Project Settings → Vault (it may also appear under Integrations).
  3. Create a secret named login_hook_secret and paste the value in.
  4. Keep the same value handy — it goes into your hosting environment as LOGIN_HOOK_SECRET in Section 07.
Why use Vault instead of typing it in the function?

If you paste the secret directly into the database function, anyone who can read your function definitions can read your secret. Vault keeps it encrypted and out of the function body.

4.6  Why the Webhooks dashboard UI probably won't work

You may be tempted by Dashboard → Database → Webhooks, which offers a friendly point-and-click way to watch a table. Try it, but be aware of a real limitation:

Warning

The Webhooks UI usually only lists tables in the public schema. The table you need — auth.sessions — lives in the auth schema. So you will most likely need to create the trigger by hand in the SQL Editor rather than through the UI.

4.7  Creating the trigger — and the one rule that matters most

Concept: a database trigger
What it is
A rule that says "whenever X happens to this table, automatically run this code."
What ours does
"Whenever a new row is inserted into auth.sessions, send an HTTP POST to my API."
Why it is reliable
It lives inside the database. The app cannot skip it, disable it, or forget to call it.
Warning — the single most important detail in this guide

Wrap the entire trigger function body in an exception handler that swallows all errors.

Triggers run inside the login transaction. If your function throws an error, the session insert is rolled back — and the user cannot log in. A single typo in your notification code would lock every FitVerse user out of their account.

An exception handler ending in exception when others then return new; guarantees that a broken notifier can never prevent a login. Do not skip this.

What the function should do, in order

  1. Try to read the secret from Vault.
  2. Call net.http_post with your endpoint URL, a JSON body, and the headers below.
  3. Catch and swallow every possible error, always letting the login proceed.

Trigger settings

SettingValue
TimingAFTER INSERT — never BEFORE. "After" means the login has already succeeded before your code runs.
Tableauth.sessions
For eachROW — run once per new session, not once per statement.
HTTP methodPOST
URLhttps://fitverse.app/api/auth/login-notify — your deployed URL, not localhost.
HeadersContent-Type: application/json
x-fitverse-hook-secret: <your secret>

The JSON body it should send

{
  "session_id":  "<the new session's id>",
  "user_id":     "<the new session's user_id>",
  "occurred_at": "<created_at>",
  "user_agent":  "<user_agent, or null>",
  "ip":          "<ip, or null>"
}
Tip — send the raw IP, store the hashed one

Send the raw IP address here. Your API route hashes it on arrival using the existing hashIP() function. That way the real IP travels over encrypted HTTPS but is never written to disk. Same approach your waitlist route already uses.

Section 05 · Step 2

Create the Database Table

One table, login_events, does three jobs at once: it is your logbook, your duplicate-blocker, and your retry list. Run this SQL yourself in the Supabase SQL Editor.

5.1  The SQL migration

create table public.login_events (
  id               uuid primary key default gen_random_uuid(),
  session_id       uuid not null unique,
  user_id          uuid not null references auth.users(id) on delete cascade,
  occurred_at      timestamptz not null,

  user_agent       text,
  ip_hash          text,

  email_status     text not null default 'pending'
                   check (email_status in ('pending','sent','failed','skipped')),
  email_sent_at    timestamptz,
  email_error      text,
  email_attempts   int not null default 0,

  created_at       timestamptz not null default now()
);

create index login_events_user_time_idx
  on public.login_events (user_id, occurred_at desc);

create index login_events_retry_idx
  on public.login_events (email_status)
  where email_status in ('pending','failed');

create index login_events_digest_idx
  on public.login_events (occurred_at desc);

alter table public.login_events enable row level security;

create policy "users read own login history"
  on public.login_events
  for select
  using (auth.uid() = user_id);

5.2  Every column explained

Necessary columns

ColumnWhat it is for
idThe row's own identifier. Standard practice — every table gets one. gen_random_uuid() generates a random unique value automatically.
session_idThe heart of the whole feature. Supabase's ID for this specific login. Marked unique, which means the database physically refuses to store a second row with the same value. That refusal is your duplicate-blocker.
user_idWho logged in. references auth.users(id) on delete cascade means if a user deletes their account, all their login history is deleted automatically — good for privacy compliance, and you get it for free.
occurred_atWhen the login actually happened, taken from Supabase.
email_statusWhere the email got to: pending, sent, failed or skipped. The check constraint means a typo like 'sentt' is rejected by the database rather than silently stored.
created_atWhen you recorded the row. Differs from occurred_at if a retry ran later — useful when debugging.

Useful columns

ColumnWhat it is for
user_agentThe raw browser/device text string. You convert it into friendly wording like "Chrome on Windows" when writing the email.
ip_hashThe scrambled IP address. Lets you notice "20 logins from one place" without ever storing anyone's actual address.
email_sent_atThe moment the email went out. Useful for spotting delays.
email_errorThe error message if sending failed. Without this you will never know why an email didn't arrive.
email_attemptsHow many times you have tried. Lets your retry job give up after three attempts instead of looping forever.

Columns I have deliberately left out

ColumnWhy it is not there
email You asked for it, and I would skip it. Storing the address duplicates personal data that can go out of date, and you can always fetch the current one from auth.users when you need it. One less copy of personal data is one less thing to protect.
admin_notified Unnecessary once you use a digest. The digest simply asks "show me everything from the last 24 hours" using occurred_at. A per-row flag would be bookkeeping you never read.
Approximate location Needs a paid third-party IP-lookup service — an extra dependency and an extra cost. Skip it in version 1. Time plus device is enough for someone to recognise their own login. Add it later if you want.

5.3  Keys, constraints and indexes explained

Concept: primary key
What it is
The column that uniquely identifies each row — here, id.
Why we need it
So you can point at one specific row to update it (for example, to change email_status from pending to sent).
Concept: unique constraint on session_id
What it is
A rule telling the database "this value may appear at most once in this whole table."
Why it is the most important line in the migration
To prevent the same login email being sent twice, every login session gets a unique ID. The database allows that ID to appear only once. If Supabase accidentally sends the same event again, the database recognises the session already exists, rejects the insert, and your code simply skips sending another email.
Why it must live in the database, not in your code
Serverless functions can run several copies of themselves at the same instant. Two copies could both ask "does this exist?", both get told "no", and both send an email. The database cannot make that mistake — a unique constraint is enforced at the storage layer, where only one write can win.
Concept: indexes
What they are
Like the index at the back of a book — a shortcut that lets the database find rows without reading every single one.
The three we create
login_events_user_time_idx — makes "show me this user's recent logins" fast. You will want a "recent activity" screen eventually.
login_events_retry_idx — makes "find all emails that failed" fast. This is a partial index: it only covers pending and failed rows, so it stays small.
login_events_digest_idx — makes "show me everything from the last 24 hours" fast, for the admin digest.

5.4  Row Level Security — why nobody sees another user's history

Concept: Row Level Security (RLS)
What it is
A PostgreSQL feature where the database itself decides, row by row, who is allowed to see what.
Why it beats checking in your code
If the rule lives in your application code, every new query is a new chance to forget it. If it lives in the database, it cannot be forgotten — the protection applies to every query from everywhere, automatically.

Three layers protect this table:

  1. enable row level security — flips the default to deny everything. With RLS on and no matching policy, nobody reads anything at all.
  2. The select policy — auth.uid() = user_id tells the database to compare the currently-logged-in user's ID against the row's owner. A user asking for someone else's rows gets an empty result, not an error — so there is nothing to probe at or guess from.
  3. No insert, update or delete policies — deliberately absent. This means no ordinary user can ever write to this table, only read their own rows. Only your server writes.
Important — how your server writes to a protected table

getSupabaseAdmin() in lib/supabase.ts uses the service role key, which bypasses RLS entirely. That is correct and intended — your backend needs to write rows for any user.

But it is exactly why that key must never reach a browser. RLS is your wall; the service role key is the master key that opens every door in it.

6.2  Three deliberate differences from the waitlist route

You are copying that file's patterns, but three things must change. Understanding why each one changes will teach you more than the code itself.

1 — No CORS headers

The waitlist route has secureHeaders() because a browser calls it, and browsers require CORS permission. This endpoint is called by your database, server to server. Browsers should never touch it, so adding CORS would only widen your attack surface for no benefit. Leave it out.

2 — Do not copy the in-memory rate-limit Map

The waitlist route keeps a counter in memory (line 8). On serverless hosting, each running instance gets its own memory, so the limit is unreliable — a fact worth knowing about that route too.

Here you do not need it. The shared secret stops strangers and the unique session ID stops repeats. Both are far stronger guarantees than a counter.

3 — Await the email instead of fire-and-forget

The waitlist route fires the email and forgets it (line 145) because a real person is staring at a loading spinner, waiting for a response.

Here, nobody is waiting. The login already finished several steps ago. So you can safely await the send and record whether it actually worked — which is what makes retries possible.

6.3  The logic, step by step

STEP 1 — Check the secret, before anything else

Read the x-fitverse-hook-secret header and compare it to process.env.LOGIN_HOOK_SECRET. If missing or wrong → return 401 and stop immediately. Do nothing else — do not parse the body, do not log it.

Concept: timing-safe comparison
What it is
A way of comparing two secrets that always takes exactly the same amount of time, regardless of how similar they are. In Node.js: crypto.timingSafeEqual.
Why a normal === is unsafe
A normal comparison stops at the first wrong character. So comparing "abc..." takes microscopically longer than "xbc..." if your secret starts with "a". An attacker who measures thousands of requests can use those tiny differences to guess your secret one character at a time. This is called a timing attack.
What you do
Use crypto.timingSafeEqual instead of === for the secret check. Everywhere else, === is fine.

STEP 2 — Parse the JSON

Wrap request.json() in a try/catch → return 400 on malformed JSON. Identical to waitlist route lines 100–107.

STEP 3 — Validate with Zod

Build a schema requiring session_id (uuid), user_id (uuid) and occurred_at (datetime), with user_agent and ip optional/nullable. Use safeParse → return 422 on failure, exactly like waitlist route lines 110–116.

Why validate at all, if only Supabase calls this?

Because "only Supabase calls this" is an assumption, and security means not relying on assumptions. Validation also catches your own mistakes — a typo in the trigger's JSON body shows up as a clean 422 in your logs instead of a confusing database error later.

STEP 4 — Hash the IP

Call your existing hashIP() if an IP came through. Note the difference from the waitlist route: there, the IP is read from request headers because the user's browser makes the call. Here, the IP arrives in the request body, because the caller is your database, not the user.

STEP 5 — Insert the row first, before sending anything

Insert with email_status: 'pending'. Writing the record before attempting the email is what makes retries possible — if the send fails, you still have a record saying "this one needs another try".

STEP 6 — Catch error 23505

Check for it the same way waitlist route lines 127–131 does. If it fires, this session has already been handled — return 200 immediately and send no email.

This is the entire duplicate defence, and it is one if statement. For any other database error: log it and return 500.

Concept: PostgreSQL error 23505
What it is
The standard error code PostgreSQL returns for "unique constraint violated" — meaning "you tried to insert a value that already exists".
Why you check the code, not the message
Error messages are written for humans and can change between database versions or languages. Error codes are stable and standardised.
Where you have seen it before
Your waitlist route already uses it to detect somebody signing up twice with the same email. Same code, same technique, new purpose.

STEP 7 — Look up the user's email address

The session data contains no email address, only a user ID. Use the admin client:

getSupabaseAdmin().auth.admin.getUserById(user_id)

This requires the service role key, which you already have configured. Pull out the email address and any display name stored in the user's metadata.

STEP 8 — Handle a missing email address

If there is no address, update the row to email_status: 'skipped' and return 200. This is not an error — there is simply nothing to send.

STEP 9 — Send via Resend

Import the existing resend object from lib/resend.ts. Use the same call shape as waitlist route lines 146–152, but with: 

from: "FitVerse Security <security@fitverse.app>"

and your new login template. Wrap the await in a try/catch.

STEP 10 — Record the outcome

  • Success → set email_status: 'sent', email_sent_at to now, increment email_attempts.
  • Failure → set email_status: 'failed', store the message in email_error, increment email_attempts.

STEP 11 — Return 200 either way

Important — this bit is counterintuitive

Even if the email failed, return 200.

A non-2xx response tells the caller "please retry me" — and pg_net will not retry anyway. So returning 500 achieves nothing except noise in your logs. The failure is already recorded in the row, which is exactly where your retry job will look for it.

Return 200 with a small body like { handled: true, email: "failed" } so your logs stay readable and honest.

Reserve non-200 responses for:

  • 401 — bad or missing secret
  • 400 / 422 — malformed or invalid request
  • 500 — genuine server error, e.g. the database is unreachable

Section 10 · Step 7

Duplicate Protection

10.1  The idea, in everyday terms

The cloakroom ticket

Think of a cloakroom ticket. You hand over your coat and get ticket #4471. If you turn up with #4471 a second time, the attendant says "already collected" — they do not hand you a second coat. The ticket number is unique, so it can only be redeemed once.

session_id is the ticket. The unique constraint is the attendant. Even if your API is called five times with the same session ID, only the first insert succeeds — the other four hit error 23505 and get turned away.

Important — why the check must live in the database

Serverless functions can run several copies of themselves at the same instant. Two copies could both check "does this exist?", both be told "no", and both send an email.

The database cannot make that mistake. A unique constraint is enforced at the storage layer, where only one write can possibly win. This is why we do not write duplicate-checking logic in TypeScript.

10.2  Every scenario, and exactly what happens

What happens New session? Email? Why
User types email + password and signs in Yes YES This is the real thing. Exactly what you want.
Supabase sends the webhook twice No — same session No Second insert hits 23505; the route returns 200 and stops.
User refreshes the page No No The existing session is reused. Nothing new is created.
App is closed and reopened No No The saved session is restored, not recreated.
Token refreshes (roughly hourly) No No The key one. A refresh updates the existing session's timestamp — it does not insert a new row. Your trigger only fires on INSERT, so it never runs at all.
Session restored from storage No No Nothing is inserted, so nothing fires.
User logs out, then logs back in Yes, brand new YES New session, new ID, new email. Correct — this genuinely is a new login.
Same person on phone and laptop Two sessions TWO Correct — two devices are two things worth knowing about.
Tip — the insight worth remembering

The scenario you were most worried about — the hourly token refresh — is handled by physics rather than by logic. There is no INSERT, so there is no trigger, so there is no email. Nothing to configure, nothing to get wrong.

This is precisely why the server-side design beats client-side detection. You are not filtering out false alarms — they never occur in the first place.

Section 11 · Step 8

Failure Handling

The governing rule of this entire feature

A failed email must NEVER prevent a user from logging into FitVerse.

Your architecture enforces this structurally — the notification runs after the login, in a separate process. Even total failure of every component below leaves login completely untouched.

11.1  Every failure scenario

# Situation What happens to login What happens to the email
1API route is down Unaffected — works normally net.http_post queues the call, it fails, the database moves on. No email, no record.
2Resend is down Unaffected — works normally Row is already saved as pending. The send throws, gets caught, row is marked failed with the error text. The retry job picks it up later. Nothing is lost.
3Database insert fails (not a duplicate) Unaffected — works normally Logged, route returns 500. No email, no record. Rare, and visible in monitoring.
4Email sending fails Unaffected — works normally Same as #2 — recorded as failed, not lost.
5Webhook fires twice Unaffected — works normally Second insert hits 23505 → return 200, no second email.
6User has no email address Unaffected — works normally Row marked skipped, return 200. Not treated as an error.
7Invalid request body Unaffected — works normally Zod rejects it → 400 or 422. Nothing saved, nothing sent.
8Someone calls the endpoint manually Unaffected — works normally No valid secret → 401 immediately, before any parsing. Nothing saved, no email. This is the attack you most need to block — otherwise anyone could spam a user's inbox with fake alerts.
9Same session ID submitted twice Unaffected — works normally Same as #5. The database refuses it.
Tip — notice the pattern

Every single row says login is unaffected. That is not luck — it is what "trigger fires after the login, in a separate process, wrapped in an exception handler" buys you. The safety is designed in, not bolted on.

11.2  The retry job

Build this after the main flow works.

A scheduled task that finds rows where email_status is 'pending' or 'failed' and email_attempts < 3, then tries sending again. The login_events_retry_idx index exists for exactly this query.

Important — do not retry forever

Cap it at three attempts. After that, leave the row marked failed and let the daily digest surface it. Infinite retries turn one broken email into thousands of pointless API calls, and can get your Resend account rate-limited.

Section 12 · Step 9

Security & Privacy

Each item below includes why it matters. Security checklists you follow without understanding are the ones you quietly skip when you are in a hurry.

12.1  Secrets

  • LOGIN_HOOK_SECRET is 32+ random characters from a password manager — not something you typed.
    Why: human-invented strings are guessable; generated ones are not.
  • The same value exists in Supabase Vault and your hosting environment — and nowhere else.
    Why: every extra copy is another place it can leak from.
  • Compared with crypto.timingSafeEqual, never ===.
    Why: prevents timing attacks that reveal your secret one character at a time.
  • The trigger function reads it from Vault, not hardcoded in the function body.
    Why: anyone who can read your database functions would otherwise read your secret.
  • SUPABASE_SERVICE_ROLE_KEY has no NEXT_PUBLIC_ prefix — already correct in lib/supabase.ts.
    Why: this key bypasses all security rules. In a browser it is total database compromise.
  • RESEND_API_KEY likewise — already correct in lib/resend.ts.
    Why: a leaked key lets anyone send email as FitVerse.
  • .env added to .gitignore — currently only .env*.local is covered.
    Why: a secret committed to git is compromised permanently, even after deletion.
  • No secret ever appears in a response body or an error message.
    Why: error responses get logged, screenshotted and pasted into chat.

12.2  The endpoint

  • Secret is checked first, before parsing anything at all.
    Why: gives an attacker the smallest possible surface to interact with.
  • POST only; GET returns 405.
    Why: reduces accidental exposure and search-engine crawling.
  • No CORS headers — this is server-to-server.
    Why: CORS would invite browser traffic you never want.
  • Every input validated by Zod before it touches the database.
    Why: malformed data becomes a clean 422 instead of a confusing database error.
  • Error responses are generic; real details go only to console.error, matching waitlist route line 137.
    Why: detailed errors tell attackers how your system is built.

12.3  Data protection

  • RLS enabled on login_events, with only a read-your-own policy.
    Why: makes leaking another user's login history structurally impossible, not just unlikely.
  • IPs hashed with your existing hashIP() — raw IPs never stored.
    Why: you keep the ability to spot patterns without holding data that can locate someone.
  • IP_HASH_SALT is set to a real value in production.
    Why: waitlist route line 27 falls back to the literal string "fitverse-salt", which is visible in your source code and therefore public. A known salt makes hashes reversible by brute force. Check this one.
  • A retention policy — delete rows older than 90 days on a schedule.
    Why: data you no longer hold cannot be breached, subpoenaed or leaked.
  • on delete cascade means account deletion removes login history automatically.
    Why: satisfies "right to erasure" without anyone remembering to do it manually.

12.4  Rate limiting

  • Do not copy the in-memory Map from the waitlist route.
    Why: on serverless, each instance has separate memory, so the limit does not reliably hold.
  • The unique constraint plus the shared secret are your real protections.
    Why: both are enforced in places an attacker cannot reach.
  • Optionally add a per-user cooldown query.
    Why: so somebody logging in 20 times an hour does not receive 20 emails and learn to ignore them.

12.5  Logging

  • Never log full request bodies containing personal data.
    Why: logs are widely readable, retained a long time, and often shipped to third-party services.
  • Log outcomes and error codes, not payloads.
    Why: gives you everything needed to debug, without creating a second copy of personal data.

12.6  Privacy and compliance

Warning — a compliance step you must not skip

Update app/privacy/page.tsx. Its "Information We Collect" list does not currently mention login metadata. Under India's DPDP Act, you should be able to state what you collect, why you collect it, and how long you keep it.

  • Add login metadata (time, device, hashed IP) to the Privacy Policy's collection list.
    Why: legally required, and it is the honest thing to do.
  • State the 90-day retention period explicitly.
    Why: "how long" is a specific requirement under both DPDP and GDPR.
  • Say that security alerts are transactional and have no unsubscribe link.
    Why: this is normal and legal for security messages — but you must say so, rather than leaving people confused about why they cannot opt out.
  • Mask the email address inside the email itself.
    Why: limits exposure if the message is forwarded or shown on a shared screen.

Tip — the universal first question

Whenever something is not working, ask: "Is there a row in login_events, and what does its email_status say?"

  • No row → the problem is in Supabase (trigger, pg_net, or the secret).
  • Row says pending → your route crashed midway.
  • Row says failed → read email_error; it usually names the cause.
  • Row says sent → the problem is deliverability, not code. Go to Problem 2.

Problem 7 — Database permission or RLS errors

Possible causeWhat to checkHow to fix it
Using the anon client instead of adminAre you calling getSupabaseAdmin()?The anon client obeys RLS and cannot write. Use the admin client in the API route.
RLS enabled with no policyDoes the read-own policy exist?With RLS on and no policy, users see nothing. Add the policy from Section 05.
User sees an empty list, expected dataDoes auth.uid() match user_id?RLS returns empty results rather than errors — that is by design, so check the IDs match.
Foreign key violation on insertDoes that user_id exist in auth.users?Deleted users cannot have new login events. Handle it gracefully.

Problem 8 — Missing environment variable or invalid secret

Possible causeWhat to checkHow to fix it
Every request returns 401Compare the Vault value against the hosting value, character by characterA trailing space or newline when pasting is the usual culprit.
Variable added but not appliedHave you redeployed since adding it?Most hosts only pick up new environment variables on the next deployment.
Added to Preview but not ProductionWhich environment the variable is scoped toAdd it to Production explicitly.
IP_HASH_SALT missingIs it set in production?It silently falls back to a value visible in your source code, which weakens the hashing.
